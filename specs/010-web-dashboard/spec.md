# 特性规格：Web trace 看板

**特性分支**：`010-web-dashboard`
**状态**：已完成

## 目标

让运维者在浏览器中看到智能体做了什么：提交一个目标、观察一次运行的进展、回应它提出的提示，并阅读每个步骤的路由概率、策略决策、执行结果与延迟。看板不增加任何智能体行为，也不改动 `jev_router` 或 `apps/api` 中的任何契约；它只消费第 9 阶段已经暴露的 HTTP 边界。

## 用户故事

### US1 - 看清路由层做了什么决定

作为运维者，我需要每个步骤都展示 Jev 返回的路由信号、每个信号所对照的阈值，以及策略引擎所选择的控制结果，这样我才能判断某个步骤为何被执行、被升级或被停止。

验收场景：

1. 每个步骤都以 0–1 的计量条展示 `route_confidence`、`requires_confirmation` 与 `needs_reasoning`，并标出文档中记载的阈值。
2. `route_risk` 与 `quality_score` 与各自的阈值并列，以原始数字展示，绝不作为 0–1 计量条，因为供应商的 score 字段并未被核心包归一化。
3. 每个步骤都原样展示策略结果及其原因。
4. 未执行的步骤会说明自己未执行，被否决的确认会说明自己已被否决。
5. 每个步骤都以毫秒展示其耗时。

### US2 - 从整体上跟随一次运行

作为运维者，我需要一个任务层面的视图，展示状态、步骤数、诊断信息以及有序的步骤链条，这样我才能看出运行停在了哪里。

验收场景：

1. 头部展示实时状态（`running`、`awaiting_confirmation`、`awaiting_input`）或终态 `RunStatus`、步骤数，以及存在时的诊断信息。
2. 步骤链条按步骤顺序渲染，每个步骤带其动作与结果。
3. 视图在运行处于实时状态时刷新，一旦运行进入终态就停止刷新。

### US3 - 为运行解除阻塞

作为运维者，我需要不离开任务页面就能批准或否决一个待处理的动作，并回答一个待处理的问题。

验收场景：

1. 待处理的确认会展示该动作及其已解析的参数，以及批准与否决按钮。
2. 待处理的输入会展示该问题与一个文本框。
3. 回应之后视图会刷新；因运行已继续而返回的 `409` 会被报告出来，而不是被吞掉。

### US4 - 启动一次运行

作为运维者，我需要从浏览器提交一个目标，并落到新任务的页面上。

验收场景：

1. 首页带有一个目标字段与一个可选的上下文字段。
2. 成功提交后会导航到新任务。
3. 被 API 拒绝的目标（`422`）会展示 API 的消息，而不是一条笼统的失败提示。

### US5 - 信任这条边界

作为运维者，我需要看板不持有任何凭据，并且在 API 不可达时诚实地失败。

验收场景：

1. Web 应用中没有配置任何供应商凭据，也不会发送任何凭据；浏览器只与 Next.js 服务器通信。
2. 当 API 无法访问时，页面会说明这一点并指出所配置的上游，而不是渲染一次空的运行。
3. 未知的任务 id 会渲染一个未找到页面，而不是一堆错误栈。

## 需求

- **FR-001**：在 `apps/web/` 下提供一个 Next.js 应用，渲染任务列表、任务详情视图，以及 API 返回的每条步骤 trace。
- **FR-002**：每一次 API 调用都在服务端进行。浏览器绝不直接调用 `apps/api`，且 Web 应用不配置任何凭据。
- **FR-003**：从 `API_UPSTREAM_URL` 读取上游基础 URL，其文档化默认值为 `http://127.0.0.1:8000`。
- **FR-004**：按间隔刷新实时任务视图，并在运行到达终态状态后停止刷新。
- **FR-005**：在任务页面回应用户的确认与输入提示，并把过期答案导致的 `409` 暴露出来。
- **FR-006**：只为 API 报告为 0–1 的值绘制概率计量条。把 `route_risk` 与 `quality_score` 作为原始数字对照其阈值来渲染。
- **FR-007**：只渲染 API 响应中存在的值；绝不插值、编造或平滑任何缺失的字段。
- **FR-008**：保持 `jev_router/` 与 `apps/api/` 不变。
- **FR-009**：让视图模型层保持纯粹，并对其做离线单元测试；`tsc --noEmit`、`next build` 与 vitest 套件是本阶段检查的一部分。
- **FR-010**：在 TypeScript 中镜像 `apps/api/schemas.py`，并把该镜像记录为一份必须在 API 变化时同步更新的副本。

## 成功标准

- 通过看板提交的一次运行会出现在列表中，并展示每个步骤的概率、策略结果、结果与耗时。
- 待处理的确认可以在任务页面被批准或否决，运行会相应地继续或停止。
- `next build`、`tsc --noEmit`、vitest 套件与既有的 Python 检查全部通过，且 `jev_router/` 或 `apps/api/` 下没有任何改动。

## 非目标

- 认证、授权、多用户访问与限流。
- 流式输出、服务器推送事件或 WebSocket。API 一个都不提供，因此视图采用轮询。
- 改动 `apps/api`，包括增加一个在重启后列出已持久化运行的端点。按第 9 阶段的设计，运行注册表是内存中的，因此指向已重启 API 的看板不会显示任何任务；弥补这一缺口属于后续阶段。
- 评测运行器与对比看板。
- 组件库或设计系统；看板使用 Tailwind 工具类与一小组本地组件。
- 在浏览器中持久化当前视图之外的任何内容。
