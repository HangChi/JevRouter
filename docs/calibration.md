# 阈值校准

策略引擎靠四个阈值决定「自动执行 / 请人确认 / 交给 LLM」。它们从哪来？第一版凭经验，之后就应当由数据决定。这份文档说明怎么用评测数据把它们调准，以及**为什么大多数时候不该调**。

## 为什么需要校准

`doc.md` 里写的是 `0.75 / 2.5 / 0.70 / 0.75`，并明确标注「不是 Jev 官方推荐值，而是 MVP 的初始值」。四个数字决定了整个系统愿意让机器自己走多远，凭手感定下来的话，等于把安全边界交给猜测。

校准要回答的问题是：**在这批真实用例上，换一组阈值会不会更好？**

## 两个前提

1. **有带信号报告。** 每条用例必须记录 `confidence`、`risk`、`requires_confirmation_probability`、`needs_reasoning_probability`、`tool_risk`。早期报告没有这些字段，`calibrate` 会把它们计为「无法重放」并跳过。
2. **不调用 provider。** 校准在已记录的信号上重放策略引擎，零成本、可反复跑。它不是再跑一遍评测。

## 工作流

```sh
# 1. 跑一次真实评测，产出带信号的报告（这一步花钱）
uv run --env-file .env python -m evals --mode compare --json-out evals-report.json

# 2. 在报告上搜阈值网格（这一步不花钱）
uv run python -m evals --mode calibrate --from-report evals-report.json --top 10

# 3. 把采纳的值写进 .env，而不是改代码里的默认值
```

第 2 步也可以把结果存成 JSON 供后续比对：

```sh
uv run python -m evals --mode calibrate --from-report evals-report.json \
  --top 10 --json-out evals-calibration.json
```

## 它怎么打分

每个候选阈值组合会被拿去重放全部可重放用例，逐条判断策略结论（执行 / 确认 / 委托 / 拒绝），然后统计：

| 计数 | 含义 |
| --- | --- |
| `executed` / `confirmed` / `delegated` | 三种结局各多少条 |
| `executed_wrong` | **动作不在允许集里，却被自动执行了** |
| `confirmed_wrong` | 动作错了，但停下来问了人 |
| `confirmation_mismatches` | 实际是否确认，与用例期望不符的条数 |

得分是一个显式的偏好声明，写在 `evals/calibrate.py` 顶部：

```
得分 = 正确自动执行 × 1.0
     + 错误自动执行 × (−2.0)
     + 错误确认     × (−0.5)
```

为什么这样配：把正确的动作自动执行掉是收益；把错误的动作自动执行掉是**唯一真正危险的事件**，所以重罚；把错误动作交给人工确认仍有成本（浪费一次注意力），但比机器直接做错轻。

排序键是：

```
(−得分, 确认失配数, 委托次数, 更保守的阈值)
```

前两项是质量，第三项是成本，第四项是**同分时的取向**。这一项容易被写错，下面单独说。

## 同分时偏向哪边

「更保守」在两个方向上不是同一个符号：

| 维度 | 提高阈值 | 更保守的方向 |
| --- | --- | --- |
| `confidence` | 更多步骤交给 LLM | **提高** |
| `reasoning` | 更多步骤交给 LLM | **提高** |
| `confirmation` | 更少动作要求批准 | **降低** |
| `risk` | 更少动作要求批准 | **降低** |

原因是前两者「高 = 更容易委托」，后两者「低 = 更容易拦下」。四个维度一律取高，效果是**在同分时把两个安全阀悄悄关掉**——这不是一个有意做出的决定，而是排序实现里的一处疏忽。当前实现把方向分开写，并有测试钉住。

更一般的原则：数据只能说明「这批用例上两者没差别」，说明不了「多放开一点也不会出事」。所以同分时选自动执行面更小的那一侧。

## 两种「不该照抄」的情况

工具会主动标注，因为不看标注直接抄推荐值是这类工具最常见的误用。

**`inert_dimensions`（无差别维度）**

在本批用例上无论怎么调都不改变任何一个结果。这时打印出来的推荐值只是同分里任取的一个，**改它没有任何数据支撑**。

实测那份 53 条用例的报告里，确认概率最大 0.77、风险分最大 2.56、推理概率最大 0.71——都够不到默认阈值 0.75 / 2.5 / 0.70。于是三个维度完全不起作用，输出会写：

```
· 这些维度在本批用例上无论怎么调都不改变结果：risk, reasoning。
  它们的推荐值只是同分任取，没有证据支持改动，建议保持现状。
```

**`at_boundary`（取到边沿）**

最优值正好落在搜索网格的最小或最大值上，说明真实最优可能在范围之外。这时结果只能读作「当前网格内最好」，不能当成「已找到最优点」：

```
⚠ 这些维度取到了搜索范围的边沿：risk, reasoning。
  说明真实最优可能在范围之外，这个结果只能读作「当前网格内最好」。
```

修法不是无脑扩大网格——网格无限扩大，最终会收敛到「全部委托」或「全部执行」这种退化解。合理做法是补用例，让新用例覆盖那段空白。

## 2026-10-31 的实测记录

53 条用例，Jev `jev-latest` 对 `step-5-preview` 基线。四轮运行都落在 `traces.db`，可在 `/evals` 页对照。

| run | 改动 | 期望命中 | 升级率 | 确认 |
| --- | --- | --- | --- | --- |
| `82085550` | 无（50 用例旧口径） | 56% | 56% | 0/17 |
| `b73af4cd` | 确认规则收敛到策略引擎 | 81.1% | 62.3% | 16/17 |
| `9b855385` | 改写候选动作描述 | 92.5% | 54.7% | 16/17 |
| `d517a207` | `confidence` 校准到 0.65 | 92.5% | 50.9% | 16/17 |

三条结论：

1. **确认行为的修复与阈值无关。** 旧口径下 17 条应确认用例触发 0 条；把规则收敛到一处之后立刻变成 16 条。它此前是架构缺陷，不是参数问题。
2. **准确率的瓶颈在候选描述，不在阈值。** 10 个错误里 9 个是 `ask_user` 过度触发，根因是 `knowledge_search` 的描述只讲实现（"injected set of local knowledge documents"）不讲能力边界。改描述 +5 条，调阈值 +0 条。
3. **四个阈值里只有一个有数据支撑。** `confidence` 0.75 → 0.65 让两条判断正确（conf 0.68 / 0.70）的读类动作恢复自动执行，升级 29 → 27，错误自动执行次数仍为 0。其余三个维度调了等于没调。

所以这次真正采纳的改动只有一行：

```ini
JEV_ROUTE_CONFIDENCE_THRESHOLD=0.65
```

## 校准结果的局限

- **五个阈值里只校准了四个。** 完成阈值 `JEV_COMPLETION_THRESHOLD` 不由策略引擎持有，也不在网格里——报告没记录逐用例的完成概率，工具无从重放。它只能靠人工判断，起点是这条实测：验证器对「文件已写好」这类明确完成的任务只打 0.68–0.79，够不到默认的 0.75。真正解决它的不是调阈值，而是把「路由说完成、验证器反对」改成 `needs_confirmation` 交给人——阈值因此可以留在保守的 0.75。这是校准器的已知缺口，补齐它需要让报告也记录完成概率。
- **样本量与分布。** 53 条用例覆盖不了所有边界。用例集没覆盖到的情形，校准给不出结论——它只会说「在这个范围内哪组更好」。
- **它不知道代价结构。** 得分的权重是假设，不是事实。如果一次错误的外部副作用远贵于十次多余的确认，权重应当再调。
- **它不会自动生效。** 工具只提建议，是否写回部署配置由人决定。自动改写阈值等于把安全边界交给一次运行的噪声。
- **阈值不是万能旋钮。** 这次实测就是例子：准确率的问题在提示词，阈值怎么调都动不了 5 条错误。
