# Web 仪表盘手动验证清单

对着运行中的仪表盘逐条勾选。每条都给出可直接复制的输入和应当看到的结果；看不到预期结果即为失败，先查是路由判断不同还是缺陷。

## 前提

```sh
# 终端 A：API，凭证来自仓库根目录的 .env
uv run --env-file .env uvicorn apps.api.app:create_app --factory --port 8000

# 终端 B：仪表盘
cd apps/web && npm run dev
```

浏览器打开 http://127.0.0.1:3000 。

**成本**：只有「提交任务」会产生真实 provider 调用——每步一次 route 加一次 verify，走 LLM 委托时再加一次 LLM 调用。下面按成本从低到高排列，A 组零成本。清单故意覆盖失败和拒绝分支：一条只会 happy path 的清单证明不了策略边界。

## A. 零成本（不提交任务）

- [ ] **A1 · 评测页可读**
  打开 `/evals`。
  预期：列出已记录的 run、最新一次的聚合卡片（一致率、期望命中、允许集命中、延迟、token）；点进 `/evals/{run_id}` 后一行一个用例，并排两个路由的动作与延迟。

- [ ] **A2 · 未知 task id 落 not-found**
  地址栏输入 `/tasks/deadbeef`。
  预期：not-found 页。API 应答了"不认识这个 id"，与上游不可达是两种不同的呈现。

- [ ] **A3 · 空目标被浏览器拦住**
  目标留空，点「开始运行」。
  预期：原生 `required` 拦截，不发请求（Network 面板无 `/tasks`）。

- [ ] **A4 · 非法 context 原地报错**
  目标填任意文字，上下文填 `{主题}`，提交。
  预期：表单下方红字 `context is not valid JSON: ...`，页面不跳转。

- [ ] **A5 · context 必须是对象**
  上下文分别填 `[1, 2]` 和 `5`，各提交一次。
  预期：红字 `context must be a JSON object`，均不跳转、不发请求。

## B. 单步完成（calculator，最便宜的真实 run）

- [ ] **B1 · 无确认的执行**

  ```text
  目标：计算 (12 + 8) * 3
  上下文：{"精度": "保留两位小数"}
  ```

  预期：详情页「已记录 1 步」，动作 `calculator`、策略「执行」；**不出现**「等待你处理」区块；状态「已完成」；该步结果含 `{"value": 60}`，`state_snapshot` 里能看到传入的 context。

## C. 人工确认链（重点）

- [ ] **C1 · 批准后执行**

  ```text
  目标：把这句话写进 demo/hello.txt：JevRouter 手动验证
  ```

  预期：状态先变「等待确认」，黄色区块里列出**合成后的参数**（`path` 与 `content`），不是只有动作名；点「批准」后无需手动刷新即出现下一步；仓库 `workspace/demo/hello.txt` 出现该内容；最终「已完成」。

- [ ] **C2 · 拒绝不产生副作用**

  ```text
  目标：把这句话写进 demo/rejected.txt：应当被拒绝
  ```

  预期：点「拒绝」→ 状态「已拒绝」，`workspace/` 下不产生 `demo/rejected.txt`。

- [ ] **C3 · 批准之后仍可能失败**
  重新提交 C1 那条完全相同的目标。
  预期：同样停在等待确认，批准后工具拒绝覆盖已存在的文件 → 状态「失败」并带诊断信息。这条证明确认绑定的是「即将执行的那份参数」，而不是执行一定会成功。

- [ ] **C4 · 外部副作用同样强制确认**

  ```text
  目标：给 team@example.com 发一封主题为周报的邮件
  ```

  预期：`send_mock_email` 是 external 风险，即使概率低也强制确认；批准后结果是 mock，不会真的发信。

## D. LLM 委托（最慢，单步 7–30 秒）

- [ ] **D1 · 委托分支**

  ```text
  目标：用中文写一段 80 字左右的春天简介
  ```

  预期：策略走「委托 LLM」，trace 里出现 `delegate_to_llm` 一步，LLM 生成的文本作为该步结果；等待期间 `LiveRefresh` 显示「每 2 秒刷新」，到达终态后刷新停止。

## E. 人工输入（不保证触发）

- [ ] **E1 · 询问用户**

  ```text
  目标：帮我把那个东西处理一下
  ```

  预期：路由需要更多信息时策略走「询问用户」，状态「等待输入」并出现输入框；输入答案（如 `写进 demo/note.txt`）发送后 run 继续。
  说明：是否触发取决于 Jev 当次判断，可能直接走其他分支。触发不了就跳过本条，其余用例不受影响。

## F. 失败与预算（最贵，放最后）

- [ ] **F1 · 未注册动作被拒绝**

  ```text
  目标：搜索一下最新的 AI 新闻
  ```

  预期：默认注册表只有 `calculator`、`write_file`、`send_mock_email`，没有 `web_search`（它需要调用方注入文档）→ 策略「拒绝」→ 重试到预算耗尽，终态为「预算耗尽」或「已拒绝」并留下诊断。这条会烧满 8 步 × 2 次模型调用，所以放最后。

## 收尾

- [ ] **G1 · 内存态列表的边界**
  记录 A–F 产生的 task id，重启 API 后再访问其中一个。
  预期：首页列表从空开始（页面自身也这么说明），旧 id 变为 404——`/tasks` 是 API 进程内的运行注册表，不是数据库查询。`traces.db` 里的历史 trace 不受影响，但仪表盘没有「按 id 读历史 task」的入口。

- [ ] **G2 · 上游不可达**
  停掉 API，刷新首页。
  预期：「无法读取运行列表」并点名上游地址，而不是白屏或空列表。

## 备注

- `workspace/` 默认为空，因此 C 组的文件名不会撞已有文件；`write_file` 拒绝覆盖，重复同一路径就是在测 C3。
- 每个提交的任务都会写入仓库根的 `traces.db`。想在干净的库上跑，先停掉 API 再移走该文件（schema 不自动迁移，旧库比当前构建新时会被拒绝打开）。
- 不想花钱跑确认/输入链时，可以起一个 stub 实例：`create_app(settings=..., store=TraceStore(tmp), client=<stub>, resolver=<stub>)` 接受注入这两个协作者，用 uvicorn 起在 8001，再把另一个仪表盘指向它（`API_UPSTREAM_URL=http://127.0.0.1:8001 npm run dev`，3000 被占用时会自动用 3001）。让 stub 的第一跳跨过确认阈值，C1–C3 就能在零 provider 调用下反复点击。
